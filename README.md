# Техническое задание на разработку проекта "PocketKeeper"
**Версия:** 1.0
**Дата:** 26.03.2026

## 1. Цель и назначение проекта
Разработать веб-приложение для автоматизации учета личных финансов и семейного бюджета. Система должна позволять пользователям отслеживать доходы и расходы, контролировать общий бюджет семьи (с возможностью разделения на участников) и анализировать финансовые потоки.

## 2. Функциональные требования (MVP)
Система должна обеспечивать выполнение следующих базовых сценариев:

### 2.1. Модуль пользователей и семей (аутентификация)
- Регистрация и авторизация пользователей (по email/паролю).
- Возможность создания "Семьи" (общего пространства).
- Возможность приглашать других пользователей в свою семью (генерация инвайт-кода/ссылки).
- Разграничение ролей: Администратор (владелец) и Участник (может только добавлять транзакции, но не управлять настройками семьи).
- Восстановление пароля.

### 2.2. Учет финансов
- Добавление, редактирование и удаление транзакций (Доход/Расход).
- У транзакции должны быть поля:
    - Сумма;
    - Валюта (базовая поддержка: RUB, USD, EUR);
    - Дата операции;
    - Категория (выбор из предустановленного или созданного пользователем списка);
    - Счет (откуда/куда: наличные, карта, копилка);
    - Комментарий (опционально);
    - Привязка к конкретному члену семьи (кто потратил/получил).
- Ведение баланса по каждому счету.
- Возможность перевода средств между своими счетами.

### 2.3. Категории и счета
- Пользователь может создавать собственные категории расходов/доходов (иерархия не обязательна на старте, но поля БД должны позволять).
- Пользователь может создавать несколько счетов (Наличные, Карта Сбера, Копилка и т.д.).

### 2.4. Отчетность (базовая)
- Просмотр истории операций с фильтрацией по дате, категории, счету.
    - [x] дата
    - [x] категория
    - [x] счет
- Отображение текущего баланса по всем счетам.
- Круговая диаграмма расходов по категориям за период (месяц).

## 3. Поля Базы Данных (Структура данных)
Проект использует реляционную СУБД (PostgreSQL). Ниже описана структура таблиц.

### 3.1. Таблица `users` (Пользователи)
| Поле | Тип данных | Описание |
| :--- | :--- | :--- |
| `id` | UUID (PK) | Уникальный идентификатор |
| `email` | String (unique) | Email для входа |
| `hashed_password` | String | Хеш пароля |
| `full_name` | String | Полное имя пользователя |
| `family_id` | UUID (FK) | ID семьи, к которой принадлежит пользователь |
| `role` | Enum | Роль в семье ('admin', 'member') |
| `is_active` | Boolean | Активен ли аккаунт |
| `created_at` | Timestamp | Дата регистрации |

### 3.2. Таблица `families` (Семьи)
| Поле | Тип данных | Описание |
| :--- | :--- | :--- |
| `id` | UUID (PK) | Уникальный идентификатор семьи |
| `name` | String | Название семьи (например, "Семья Ивановых") |
| `created_at` | Timestamp | Дата создания |
| `invite_code` | String | Уникальный код для приглашения (хэш) |

### 3.3. Таблица `accounts` (Счета пользователя)
| Поле | Тип данных | Описание |
| :--- | :--- | :--- |
| `id` | UUID (PK) | Уникальный идентификатор счета |
| `user_id` | UUID (FK) | Владелец счета |
| `name` | String | Название счета (например, "Кошелек") |
| `type` | Enum | Тип (cash, card, deposit) |
| `currency` | String (3) | Код валюты (RUB, USD) |
| `initial_balance` | Decimal | Инициализация баланса |
| `balance` | Decimal | Текущий баланс |
| `is_active` | Boolean | Архивирован ли счет (скрыт из выбора) |

### 3.4. Таблица `categories` (Категории)
| Поле | Тип данных | Описание |
| :--- | :--- | :--- |
| `id` | UUID (PK) | Уникальный идентификатор |
| `user_id` | UUID (FK) | Кто создал счет (инициатор ввода) |
| `family_id` | UUID (FK) | Категория видна всей семье |
| `name` | String | Название (Продукты, Кафе, Зарплата) |
| `type` | Enum | income или expense |
| `icon` | String | Ссылка на иконку (опционально) |
| `parent_id` | UUID (FK) | Для иерархии (ссылка на родителя) |

### 3.5. Таблица `transactions` (Транзакции) - **Ключевая таблица**
| Поле | Тип данных | Описание |
| :--- | :--- | :--- |
| `id` | UUID (PK) | Уникальный идентификатор операции |
| `family_id` | UUID (FK) | Принадлежность семьи (для быстрой фильтрации) |
| `user_id` | UUID (FK) | Кто создал операцию (инициатор ввода) |
| `member_id` | UUID (FK) | За кого числится трата (член семьи, `users.id`) |
| `account_id` | UUID (FK) | Счет, с которого списали/зачислили |
| `category_id` | UUID (FK) | Категория транзакции |
| `amount` | Decimal | Сумма (всегда положительная) |
| `type` | Enum | income или expense (дублируется из категории для скорости) |
| `description` | Text | Комментарий/описание покупки |
| `transaction_date` | Date | Дата операции (может отличаться от created_at) |
| `is_active` | Boolean | Активенла ли транзакция для мягкого удаления |
| `created_at` | Timestamp | Когда запись внесена в систему |
| `updated_at` | Timestamp | Когда запись обновлена в систему |

### 3.6. Таблица `invitations` (Приглашения)
| Поле | Тип данных | Описание |
| :--- | :--- | :--- |
| `id` | UUID (PK) | |
| `family_id` | UUID (FK) | В какую семью приглашают |
| `email` | String | Email приглашаемого |
| `token` | String | Уникальный токен для подтверждения |
| `status` | Enum | pending, accepted, expired |
| `expires_at` | Timestamp | |

## 4. Технологический стек (Backend & Infrastructure)

### 4.1. Backend (API)
- **Язык:** Python 3.11+
- **Фреймворк:** FastAPI
    - *Обоснование:* Высокая производительность, асинхронность, автоматическая генерация Swagger-документации, что упростит дальнейшее расширение функционала и разработку фронтенда.
- **База данных:** PostgreSQL 15+
- **ORM:** SQLAlchemy 2.0 (асинхронный режим) + Alembic (для миграций).
- **Валидация:** Pydantic (встроен в FastAPI).
- **Аутентификация:** JWT-токены (access + refresh).
- **Миграции:** Alembic.

### 4.2. Инфраструктура (Опционально/Для справки)
- **Контейнеризация:** Docker, Docker Compose (для разработки и деплоя).
- **Кэширование:** Redis (для будущих нужд: рейтинги, частые запросы статистики).
- **API-документация:** Swagger UI (доступна автоматически).

## 5. Требования к архитектуре (Расширяемость)
Поскольку система будет расширяться, заложить следующие принципы:

1.  **Модульность:** Логика должна быть разделена на модули (`auth`, `accounts`, `transactions`, `reports`, `family`).
2.  **Типизация:** Строгая типизация данных (Pydantic схемы) для избежания ошибок при добавлении новых полей.
3.  **Фоновая обработка:** Предусмотреть архитектуру для выноса тяжелых задач (генерация сложных отчетов, импорт/экспорт данных) в очередь задач (Celery + Redis/RabbitMQ).
4.  **API Версионирование:** Все эндпоинты должны быть версионированы (например, `/api/v1/transactions`), чтобы обновления не ломали старые клиенты. [Сделано]

## 6. Пользовательские интерфейсы (UI)
На данном этапе разрабатывается только **Backend API**. Однако API должен быть готов к подключению следующих клиентов:
- Single Page Application (Vue).
- Мобильное приложение (React Native / Flutter).

## 7. Требования к безопасности
- Хеширование паролей (bcrypt).
- Защита от брутфорса (лимиты запросов на логин).
- Валидация входных данных на уровне Pydantic.
- Защита от SQL-инъекций (за счет использования ORM).
- Политика CORS (ограничение доступа к API с разрешенных доменов).
- Инвайт-токены должны быть одноразовыми и иметь срок действия.
